# 0007. Entra first, then SQL auth, then Cosmos keys

- Status: Accepted
- Recorded: 2026-10-29

## Context

This matches how the target Azure SQL and Cosmos resources are actually reached. Brokered sign-in (WAM) on a managed machine is unproven.

## Decision

The sidecar authenticates with MSAL.NET using the WAM broker, falling back to device-code flow. SQL auth and Cosmos key auth are supported second and third. The sidecar keeps one credential per tenant, shared by SQL and Cosmos connections in that tenant. Tokens are held in MSAL's persisted token cache in the user profile, encrypted with DPAPI, and never written to disk unencrypted.

## Consequences

The UI never holds tokens. Whether WAM works on a managed machine is recorded in M0.

## Implementation notes (2026-10-31, issue #179)

- **Client id.** `Credentials.cs` sets no `ClientId`, so sign-in uses Azure.Identity's default public client (the Azure CLI's, per Azure.Identity's documentation; not confirmed from the binary). Users see that app on consent prompts, and tenant Conditional Access policies aimed at it apply to Panoptic too. Decided 2026-10-31 (revised the same day): keep the default public client as the default, and add a per-connection client id override (issue #262). A Panoptic registration was considered and deferred: there is no tenant to register it in, and a new multi-tenant app from an unverified publisher would likely need admin consent in managed tenants (publisher verification needs a Microsoft partner ID), so it would sign in less reliably than the default client, which Microsoft pre-approves almost everywhere. Accepted risk: a tenant's Conditional Access or a Microsoft change could block the default client; the override is the way out. Revisit if there is a tenant and a verified publisher, or a tenant does block it.
- **Token cache.** `TokenCachePersistenceOptions { Name = "panoptic" }` without `UnsafeAllowUnencryptedStorage`. On Windows, Azure.Identity persists it under `%LOCALAPPDATA%\.IdentityService\` and protects it with DPAPI for the current user. Not yet confirmed on disk: the dev machine has never signed in through Panoptic with Entra. To confirm on a machine that has, open the `panoptic` file there in a hex viewer: it must be DPAPI-protected binary, not readable JSON. A readable refresh token in it would be a High finding on its own.
