# 0007. Entra first, then SQL auth, then Cosmos keys

- Status: Accepted
- Recorded: 2026-10-29

## Context

This matches how the target Azure SQL and Cosmos resources are actually reached. Brokered sign-in (WAM) on a managed machine is unproven.

## Decision

The sidecar authenticates with MSAL.NET using the WAM broker, falling back to device-code flow. SQL auth and Cosmos key auth are supported second and third. The sidecar keeps one credential per tenant, shared by SQL and Cosmos connections in that tenant. Tokens are held in MSAL's persisted token cache in the user profile, encrypted with DPAPI, and never written to disk unencrypted.

## Consequences

The UI never holds tokens. Whether WAM works on a managed machine is recorded in M0.

## Implementation notes (2026-10-31, issue #179)

- **Client id.** `Credentials.cs` sets no `ClientId`, so sign-in uses Azure.Identity's default public client (the Azure CLI's, per Azure.Identity's documentation; not confirmed from the binary). Users see that app on consent prompts, and tenant Conditional Access policies aimed at it apply to Panoptic too. A Panoptic app registration would make sign-ins attributable, but as a multi-tenant app it needs consent in each tenant. Not decided.
- **Token cache.** `TokenCachePersistenceOptions { Name = "panoptic" }` without `UnsafeAllowUnencryptedStorage`. On Windows, Azure.Identity persists it under `%LOCALAPPDATA%\.IdentityService\` and protects it with DPAPI for the current user. Not yet confirmed on disk: the dev machine has never signed in through Panoptic with Entra. To confirm on a machine that has, check that a `panoptic` file exists there and does not start with `{` (plain JSON).
